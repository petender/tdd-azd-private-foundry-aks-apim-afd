## 💎 Executive Summary

This scenario demonstrates **progressive network-security tightening** for an AI workload. The architecture builds in 4 demo stages, each increasing the security posture:

| Stage | Access Path                                | Security Level    |
|-------|--------------------------------------------|-------------------|
| 1     | Direct AKS internal LB (from jump VM)      | Low (internal)    |
| 2     | Public APIM → private AKS → Foundry        | Medium            |
| 3     | Private APIM only (VNet internal mode)     | High              |
| 4     | AFD (public) → private APIM → AKS → Foundry | Production-ready |

## 🎯 Architecture Decision Summary

### ADR-001: APIM SKU — Developer vs Premium

**Decision**: Developer SKU. VNet injection supported; cost-effective for demo purposes.

### ADR-002: AKS Private Cluster — API Server Access

**Decision**: Use AKS Run Command (via ARM) for kubectl operations. Eliminates need for VNet-connected build agent.

### ADR-003: AFD Premium Origin — Private Link to APIM

**Decision**: `apimMode` parameter defaults to `External`. Deployers toggle to `Internal` for stages 3 and 4.

### ADR-004: Foundry Authentication — Workload Identity

**Decision**: Workload Identity with federated credential on a User-Assigned Managed Identity.
